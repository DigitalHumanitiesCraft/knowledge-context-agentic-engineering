Semantic Markdown
You are the Semantic Markdown Converter and your purpose is to convert input into Semantic Markdown format.
- Goal: Capture structured, semantic data with maximum meaning and minimal tokens
- Audience: Another language model, not a human reader

Semantic Markdown is an enhanced version of traditional Markdown:

- Maintains simplicity and readability
- Supports:
  - Hierarchical relationships
  - Sequential processes
  - Ontological data structures
- Uses:
  - Unordered lists for ontologies and class taxonomies
  - Ordered lists for sequences and processes
  - Bold for highlighting key concepts
  - Headings for organizing hierarchy
  - Code blocks for structured data snippets
- Expresses triples and semantic relationships (e.g., RDF-like structures)

You do ALWAYS:

1. Read the input very carefully!
2. Analyse the input using:
   - High-level outline
   - Detailed semantic breakdown
3. Render input as Semantic Markdown, with:
   - Succinct statements
   - Semantic assertions
   - Class/instance relationships
   - Minimal verbosity; maximal conceptual compression!

## Semantic Markdown Rules

- `#`, `##`, `###` → Hierarchical headings
- `-` (unordered list) → Class/ontology/taxonomy
- `1.`, `2.`, ... (ordered list) → Sequential steps/processes
- `bold` → Emphasize key terms/concepts
- ```` ``` ```` → Code blocks for structured data or examples
- Always prepend a metadata header:
```markdown
  ---
  title:
  keywords:
  ---
```
- You can use other structures if needed, but you have to define them!

Modeling is a key concept in the Digital/Computational Humanities
Modelling is the intentional simplification and amplification of cultural artifacts into structured representations (often computational) for specific scholarly purposes. It is an iterative, creative, and critical practice that reduces complexity to reveal patterns and relationships.

Abstraction – Selecting what matters from complex realities
Formalization – Converting implicit knowledge into explicit structures
Interpretation – Making scholarly decisions about meaning and relationships

Information Extraction with LLMs
Named Entity Recognition (NER) + Entity Classification
First detect entities (persons, goods, dates, amounts), then classify their types and roles within the accounting system – understanding that #342 "Asa Danforth Cr" is both a person AND a creditor with an account number.
Relation Extraction
Map who owes whom, which transactions settle previous debts, and how entries connect across time – understanding that "Settled" changes an account's status.
Contextualization
Effective prompting for historical sources requires providing explicit context that the LLM cannot infer from its training data. We must explain that "settled" marks completed transactions, that "orders upon third parties" function as payment instruments, and that orthographic variations like "Wilham/Wilber/Wilbur" represent the same person in an era before standardized spelling. The prompt becomes a bridge between the historical world of the source and the computational model we're building. This contextualization enables the LLM to process the mixed currency notations as reflecting the transitional economy of 1820s New England, where colonial shilling systems coexisted with federal dollars, and to map ambiguous terms to their probable historical meanings.

Self-Consistency. https://www.promptingguide.ai/techniques/consistency 


Synthesise everything in a compact, clear and neutral DATA.md file that contains all knowledge and information about the model of the historical text.
After extraction, structuring and self-consistency checks, we want to compress the information ("Context Compression") so that we have fewer tokens (i.e. less noise / Context Rot), but the information is almost the same.

.md is a good choice.

Bear in mind that an LLM can also 'overdo' a task. For example, if you say “create a DATA.md”, it can add more to it. The other option is to reduce what already exists using the following prompt.

# Data Specification
## Source Data Structure (TEI XML)
### Document Structure
The source consists of TEI-encoded tables representing ledger pages. Each table contains rows of transaction entries with semantic markup for dates, persons, monetary amounts, and commodities.
### Key TEI Elements
- `table`: Container for ledger page entries
- `row[@ana='bk:entry']`: Individual transaction record
- `date[@when]`: ISO-formatted date markers
- `name[@ref]`: Person reference with unique identifier
- `measure`: Monetary amounts and commodities
- `abbr[@ana='bk:debit']` or `[@ana='bk:credit']`: Transaction type
### Supporting TEI Components
- `listPerson`: Registry of all persons with demographic data
- `taxonomy`: Hierarchical commodity classification
- Page breaks and line breaks preserved for reference

## Target Data Model

### Transaction Record
Each transaction requires:
- Unique identifier
- Date (ISO format)
- Primary party (typically Laban Wheaton)
- Secondary party (customer/partner)
- Transaction type (debit/credit)
- Monetary amount (dollars and cents)
- Commodity details (if applicable)
- Status (settled, pending, referenced ledger page)
- Source location (page number, entry ID)

### Person Entity
Each person requires:
- Unique identifier (from TEI @xml:id)
- Full name (forename, surname)
- Gender (from TEI person record)
- First appearance date
- Last appearance date
- Transaction count
- Total debit amount
- Total credit amount
- Associated relationships

### Commodity Classification
Hierarchical structure maintaining:
- Category identifier
- English term
- Parent category reference
- Wikidata reference (where available)

### Relationship Types
- Family relationships (spouse, parent, child, sibling)
- Business partnerships
- Employment relationships
- Institutional affiliations

## Data Processing Requirements

### TEI to JSON Transformation
The Python preprocessor must:
1. Parse TEI XML structure
2. Extract all transaction entries
3. Resolve person references to full records
4. Convert monetary notations to standardized format
5. Map commodity references to taxonomy
6. Generate derived statistics
7. Create network graph structure
8. Output single JSON file for web application

### Temporal Organization
- Group transactions by year
- Maintain chronological ordering
- Support date range queries
- Calculate rolling balances

### Network Generation
Create graph structure with:
- Nodes: Persons and organizations
- Edges: Transactions between parties
- Edge weights: Transaction frequency and total value
- Temporal layers: Annual snapshots

## Data Quality Requirements

### Validation Rules
- All person references must resolve to listPerson entries
- Dates must be valid and within 1828-1859 range
- Monetary amounts must be non-negative
- Credit/debit entries must balance per transaction set

### Missing Data Handling
- Unknown gender marked as "unknown"
- Incomplete dates use first known date in period
- Unresolved references logged for review
- Partial amounts treated as zero

## Output Format Specification

### JSON Structure
Single file containing:
- Metadata object (source info, processing date)
- Transactions array (chronologically ordered)
- Persons map (keyed by ID)
- Commodities hierarchy
- Precomputed statistics
- Network graph data per year

### Size Optimization
- Minimize property names
- Use arrays for repeated structures
- Compress whitespace
- Numeric IDs where possible

## Statistical Summaries Required

### Per Person
- Transaction count by type
- Total monetary flow
- Active date range
- Primary commodities traded
- Network centrality measures

### Per Time Period
- Transaction volume
- Active persons count
- New relationships formed
- Average transaction size
- Commodity distribution

### Global Metrics
- Total unique persons
- Total transactions
- Date range coverage
- Network density over time
- Gender participation rates
