Grundlagen

Context Window
Die maximale Anzahl an Tokens, die ein LLM gleichzeitig verarbeiten kann.

Faustregel: 
Je weniger Token im Context Window vorhanden sind, desto besser funktionieren
Es geht also darum, den “Sweet Spot” zu finden: ausreichend Kontextinformationen, aber nicht zu viele. 

Context Rot
Die progressive Verschlechterung der LLM-Performance mit zunehmender Token-Anzahl im Context Window. Spätere Tokens werden unzuverlässiger verarbeitet als frühere, unabhängig von der Aufgabenkomplexität. Ursache ist die nachlassende Präzision der Attention-Mechanismen bei steigender Kontextlänge.
Hong, Kelly, Anton Troynikov, and Jeff Huber. Context Rot: How Increasing Input Tokens Impacts LLM Performance. Chroma, 2025. https://research.trychroma.com/context-rot.

User-Centred Design is an iterative framework for developing systems through continuous refinement cycles, emphasizing understanding of physical, social, and cultural factors that influence user engagement. 
Analysis: Captures user needs, preferences, constraints, and working contexts through empirical methods to understand how users actually engage with systems.
Design: Translates analysis insights into conceptual solutions that balance theoretical precision with practical usability, aligned with user workflows and project objectives.
Prototyping: Creates representations from sketches to functional models for early testing and stakeholder feedback before full implementation.
Evaluation: Systematically assesses prototypes through user testing and validation to identify issues and verify requirements are met.

# Project Context

## Overview

Digital edition of the Laban Morey Wheaton Day Book, a collection of financial ledgers from Norton, Massachusetts (1828-1859). The project transforms TEI-encoded XML transcriptions into an interactive web application for historical research.

## Source Material

### Primary Source
- Original: Handwritten double-entry bookkeeping ledgers
- Period: 1828-1859 (31 years continuous)
- Location: Norton, Massachusetts
- Content: Financial transactions, credit relationships, business partnerships
- Author: Laban Morey Wheaton (dry goods store owner, postmaster)

### Digital Format
- Encoding: TEI XML (Text Encoding Initiative)
- Structure: Tabular entries with semantic markup
- Components: Transaction entries, person registry, commodity taxonomy
- Processing: Python transformation to web-ready format

## Historical Significance

The daybook documents:
- Economic transition from agrarian to early industrial economy
- Social networks and family business relationships
- Gender participation in credit economy
- Community institutional development
- Regional commerce patterns in antebellum New England

## Research Applications

### Economic History
- Credit network analysis
- Price and commodity tracking
- Business relationship evolution
- Market integration patterns

### Social History
- Family economic strategies
- Gender roles in commerce
- Institutional affiliations
- Community power structures

### Digital Humanities
- Network visualization methodologies
- Temporal analysis techniques
- Historical data modeling
- TEI to interactive visualization pipeline

## Target Audience

### Primary Users
- Social historians researching 19th century America
- Economic historians studying early capitalism
- Digital humanities researchers
- Graduate students in historical methods

### Secondary Users
- Undergraduate students
- Local history researchers
- Genealogists
- General public interested in historical economics

## Project Scope

### Included
- Complete transaction record visualization
- Person and organization network analysis
- Temporal evolution display
- Gender and institutional filtering
- Data export capabilities

### Excluded
- Editorial annotations
- Paleographic details
- Physical ledger descriptions
- Related manuscript materials

# Data Specification
## Source Data Structure (TEI XML)
### Document Structure
The source consists of TEI-encoded tables representing ledger pages. Each table contains rows of transaction entries with semantic markup for dates, persons, monetary amounts, and commodities.
### Key TEI Elements
- `table`: Container for ledger page entries
- `row[@ana='bk:entry']`: Individual transaction record
- `date[@when]`: ISO-formatted date markers
- `name[@ref]`: Person reference with unique identifier
- `measure`: Monetary amounts and commodities
- `abbr[@ana='bk:debit']` or `[@ana='bk:credit']`: Transaction type
### Supporting TEI Components
- `listPerson`: Registry of all persons with demographic data
- `taxonomy`: Hierarchical commodity classification
- Page breaks and line breaks preserved for reference

## Target Data Model

### Transaction Record
Each transaction requires:
- Unique identifier
- Date (ISO format)
- Primary party (typically Laban Wheaton)
- Secondary party (customer/partner)
- Transaction type (debit/credit)
- Monetary amount (dollars and cents)
- Commodity details (if applicable)
- Status (settled, pending, referenced ledger page)
- Source location (page number, entry ID)

### Person Entity
Each person requires:
- Unique identifier (from TEI @xml:id)
- Full name (forename, surname)
- Gender (from TEI person record)
- First appearance date
- Last appearance date
- Transaction count
- Total debit amount
- Total credit amount
- Associated relationships

### Commodity Classification
Hierarchical structure maintaining:
- Category identifier
- English term
- Parent category reference
- Wikidata reference (where available)

### Relationship Types
- Family relationships (spouse, parent, child, sibling)
- Business partnerships
- Employment relationships
- Institutional affiliations

## Data Processing Requirements

### TEI to JSON Transformation
The Python preprocessor must:
1. Parse TEI XML structure
2. Extract all transaction entries
3. Resolve person references to full records
4. Convert monetary notations to standardized format
5. Map commodity references to taxonomy
6. Generate derived statistics
7. Create network graph structure
8. Output single JSON file for web application

### Temporal Organization
- Group transactions by year
- Maintain chronological ordering
- Support date range queries
- Calculate rolling balances

### Network Generation
Create graph structure with:
- Nodes: Persons and organizations
- Edges: Transactions between parties
- Edge weights: Transaction frequency and total value
- Temporal layers: Annual snapshots

## Data Quality Requirements

### Validation Rules
- All person references must resolve to listPerson entries
- Dates must be valid and within 1828-1859 range
- Monetary amounts must be non-negative
- Credit/debit entries must balance per transaction set

### Missing Data Handling
- Unknown gender marked as "unknown"
- Incomplete dates use first known date in period
- Unresolved references logged for review
- Partial amounts treated as zero

## Output Format Specification

### JSON Structure
Single file containing:
- Metadata object (source info, processing date)
- Transactions array (chronologically ordered)
- Persons map (keyed by ID)
- Commodities hierarchy
- Precomputed statistics
- Network graph data per year

### Size Optimization
- Minimize property names
- Use arrays for repeated structures
- Compress whitespace
- Numeric IDs where possible

## Statistical Summaries Required

### Per Person
- Transaction count by type
- Total monetary flow
- Active date range
- Primary commodities traded
- Network centrality measures

### Per Time Period
- Transaction volume
- Active persons count
- New relationships formed
- Average transaction size
- Commodity distribution

### Global Metrics
- Total unique persons
- Total transactions
- Date range coverage
- Network density over time
- Gender participation rates

# Design Specification

## Design Principles

### Primary Objectives
1. Data clarity and readability for extended research sessions
2. Professional appearance appropriate for scholarly work
3. Efficient information density without clutter
4. Consistent interaction patterns across all views

### Design Philosophy
The interface should disappear in service of the data. Visual design must support, not distract from, historical analysis. Every design decision should enhance data comprehension and research efficiency.

## Visual Language

### Color Strategy

#### Semantic Colors
- Background: Near-white for reduced eye strain
- Primary text: Dark blue-gray for optimal readability
- Secondary text: Medium gray for hierarchy
- Interactive elements: Professional blue for actions
- Debit indicators: Subtle red
- Credit indicators: Subtle green
- Selection/highlight: Amber for visibility
- Borders: Light gray for structure

#### Color Application Rules
- Minimize color use to essential semantic distinctions
- Ensure 4.5:1 contrast ratio minimum
- Use color consistently across all views
- Provide non-color indicators for accessibility

### Typography Requirements

#### Type Hierarchy
- Display headings: Large, clear section identification
- Panel headers: Medium weight for subsection clarity
- Body text: Optimized for extended reading
- Data text: Monospace for numerical alignment
- Historical quotes: Serif for period authenticity
- Metadata: Small, unobtrusive labeling

- Line length: 45-75 characters for prose
- Line height: 1.5x minimum for body text

# Technical Architecture

## System Overview

### Architecture Pattern
Single Page Application with preprocessed data. Python preprocessor transforms TEI XML to JSON, which is loaded by a client-side JavaScript application. No server-side runtime required after initial data processing.

### Technology Decisions
- HTML5 for semantic document structure
- CSS3 for styling and layout
- Vanilla JavaScript ES6+ for application logic
- D3.js library for network visualizations
- Browser LocalStorage for user preferences
- Service Worker for offline capability

## Data Pipeline

### Stage 1: TEI XML Processing (Python)

#### Input Processing
The Python preprocessor (`process_tei.py`) performs:
1. TEI XML parsing and validation
2. Person reference resolution from listPerson
3. Commodity taxonomy mapping
4. Date normalization to ISO format
5. Transaction extraction and structuring
6. Relationship inference from transaction patterns

#### Data Transformation
- Convert TEI table rows to transaction objects
- Resolve person references to full records
- Calculate derived statistics
- Generate network graph structures
- Create temporal indices

#### Output Generation
- Single JSON file with complete dataset
- Minified for production deployment
- Includes metadata about processing

### Stage 2: Web Application (JavaScript)

#### Data Loading
- Fetch JSON data file on application start
- Parse and validate data structure
- Build in-memory indices for fast queries
- Cache processed data in browser

#### Runtime Processing
- Apply filters to in-memory data
- Generate visualizations dynamically
- Handle user interactions
- Maintain application state

## Application Structure

### File Organization
```

│   ├── app.js            # Application controller

│   ├── components/       # UI components
│   └── utils/            # Helper functions

#### Application Controller
Central coordinator managing:
- Application initialization
- View switching logic
- Global state management
- Event bus for components
- URL routing for deep links

#### Data Management Layer
Responsible for:
- Loading and parsing JSON data
- Maintaining data indices
- Applying filter operations
- Computing derived values
- Caching expensive calculations

#### View Controllers
Each view manages:
- Rendering its specific visualization

#### Component Layer

Ausgangslage
Problem: Mehrere Personen arbeiten an denselben DateienLösung: Versionsverwaltung verhindert Datenverlust und Versionschaos
Software
GitHub Desktop: https://desktop.github.com Grafische Benutzeroberfläche für Git-Versionsverwaltung
Initiale Einrichtung
Repository klonen - Projekt lokal verfügbar machen
Repository-URL eingebe
Lokalen Speicherort definieren
Automatischer Download aller Projektdateien

Standard-Arbeitsablauf
1. PULL - Synchronisation vom Server
Button "Fetch origin" - Aktuelle Änderungen abrufen
2. BEARBEITEN
Dateien im lokalen Projektordner bearbeiten
3. COMMIT - Lokale Versionierung
Änderungen beschreiben und lokal speichern
4. PUSH - Upload zum Server
Button "Push origin" - Änderungen für Team verfügbar machen
Arbeitsregel
Vor Arbeitsbeginn: Pull ausführen (vermeidet Konflikte)Nach Arbeitsende: Push ausführen (stellt Verfügbarkeit sicher)
